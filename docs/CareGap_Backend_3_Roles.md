# 돌봄틈새 AI — 백엔드 3명 역할 분담 및 개발 협업 계획

> **문서 상태:** 팀 업무 분담 제안서 v1.0  
> **작성 기준:** 2026-10-29 최종 통합 기능명세서 v2.0 및 백엔드 업무 분담 논의  
> **적용 범위:** iOS·Android 앱과 관리자 웹을 지원하는 백엔드  
> **주의:** 이 문서는 팀원의 역할을 배정하기 위한 **제안서**이며, 기술 스택·API 경로·세부 운영 정책이 최종 승인되었다는 뜻은 아니다.

---

## 1. 전체 역할 요약

| 구분 | 담당 영역 | 주요 책임 | 핵심 산출물 |
|---|---|---|---|
| **BE 1** | 인증·권한·사용자·관리자 | 계정/세션, 담당자 자격 심사, 대상자·가족·담당자 연결, 공통 권한·스키마 관리 | 인증 및 관계 API, 권한 정책, 기본 DB 구조, 관리자 API |
| **BE 2** | 상담·예약·기록·후속 업무·알림 | 상담 가능 시간, 예약/일정 상태, 상담 완료, 기록 및 수정 이력, 후속 업무, 푸시 알림, 2단계 통화 연동 | 예약·상담·알림 API, 상태 전이, DB 무결성/동시성 테스트 |
| **BE 3** | 파일 처리·AI·복지 정보 | 상담지 OCR, 녹음 STT, 화자 구분, AI 요약/변화/누적 분석, 원문 근거 검증, 복지사업 후보 확인 | 파일/전사/분석 API, AI 검증 파이프라인, 복지 정보 연동 |

### 팀 차원의 구조 원칙

1. **기능 단위로 소유:** 각 담당자는 자기 기능의 DB 모델, API, 비즈니스 로직, 테스트, 문서까지 책임진다. 한 사람이 모든 DB를 만들고 다른 사람이 모든 API를 만드는 방식은 지양한다.
2. **공통 계약 우선:** 사용자·대상자·담당자 식별자, 인증 주체, 상담 기록 ID, API 오류 형식은 구현에 앞서 함께 정의한다.
3. **권한은 서버에서 검증:** 화면을 숨기는 것만으로 접근 제한을 충족하지 않는다. 역할에 더해 담당자 배정·가족 연결 상태를 확인한다.
4. **원본과 결과 분리:** 상담 원문/수정본, OCR·STT 교정본, AI 초안/검토본, 후속 업무 상태를 서로 다른 데이터로 취급한다.
5. **공유 리소스 변경 통제:** 공통 스키마·권한 규칙·API 응답 형식을 변경할 때는 관련 담당자의 리뷰를 받는다.
6. **초기에는 합성 데이터 사용:** 실제 대상자 개인정보를 로컬 테스트에 넣지 않는다.

## 2. BE 1 — 인증·권한·사용자·관리자

**목표:** 누가 어떤 대상자 자료에 접근할 수 있는지 일관되게 결정하고, 나머지 백엔드가 공통으로 사용할 인증·권한 기반을 구축한다.

### 2.1 담당 기능

| 하위 영역 | 구체 작업 | 기능명세 연관 |
|---|---|---|
| 계정/인증 | 대상자·가족·담당자 가입, 로그인·로그아웃, 아이디 찾기·비밀번호 재설정, 세션 관리 | AUTH-01~03, 07~09 |
| 담당자 승인 | 소속 및 자격증 자료 접수, 승인 대기·반려·승인, 재제출, 승인 전 업무 차단 | AUTH-04~06, ADM-02~03 |
| 대상자·담당자 관계 | 업무상 담당자 연결·변경·해제·이력, 배정 여부 확인 | LINK-01~02, LINK-05 |
| 가족 연결 | 연결 요청, 대상자 허용, 연결 해제, 해제 즉시 접근 차단 | LINK-03~05 |
| 사용자/관리자 관리 | 계정·연결 현황 조회, 관리 작업 이력, 관리자 웹용 API | ADM-01~06 |
| 회원탈퇴 | 탈퇴 요청/상태 처리, 연결 해제 및 보존/삭제 정책 연계 | AUTH-10 |
| 공통 권한 모듈 | 인증된 사용자 식별, 역할·기관·가족 관계·담당자 배정 검증 | 전체 API 공통 |
| 공통 DB 운영 | 사용자/대상자/관계 기본 스키마, 마이그레이션 운영 규칙, 공통 테스트 fixture | 전체 모듈 공통 |

### 2.2 소유 데이터 예시

- `users` — 계정, 역할, 계정 상태
- `persons` — 복지 대상자 식별 정보와 계정 연결
- `staff_applications` — 담당자 자격 심사 신청과 결과
- `staff_assignments` — 대상자·담당자 배정 관계
- `family_links` — 가족 연결 요청·승인·해제 기록
- `auth_sessions` — 인증 세션/갱신 정보
- `audit_logs` — 중요 권한·관리 작업 감사 기록

> 테이블 이름은 논리 모델 예시다. 실제 명칭·분리 여부는 ERD 합의 후 결정한다. 자격증 파일은 권한이 제한된 저장소에 보관하는 구조를 협의한다.

### 2.3 API 영역 예시

- `/auth/*`: 가입, 로그인, 토큰 갱신, 로그아웃, 계정 복구
- `/users/*`, `/persons/*`: 본인 및 대상자 기본 정보
- `/staff-applications/*`: 담당자 자격증 신청/상태
- `/family-links/*`: 가족 연결 요청/허용/해제
- `/assignments/*`: 담당자 배정/변경/해제
- `/admin/*`: 관리자 심사/조회/관리

### 2.4 인수 테스트

- 승인 대기·반려 담당자는 **상담 API 자체**에 접근할 수 없다.
- 연결되지 않은 가족은 대상자 일정·기록·AI 결과를 조회할 수 없다.
- 가족 연결 해제 후 기존 URL 및 알림 딥링크로도 자료에 접근할 수 없다.
- 담당자가 배정되지 않은 대상자의 자료를 읽거나 수정할 수 없다.
- 가족이 수행한 예약 변경 등은 **가족 계정이 수행자**로 기록된다.
- 관리자에게 상담 원문 접근 권한이 자동으로 부여되지 않는다.

### 2.5 타 담당자에게 제공할 계약

- `actor`(인증 주체) 정보 및 공통 권한 검사 인터페이스
- 담당자 승인 여부/배정 여부/가족 연결 여부 검사 함수 또는 서비스
- 공유 ID 타입과 공통 에러 코드
- 권한 통합 테스트용 가상 계정/관계 fixture

## 3. BE 2 — 상담·예약·기록·후속 업무·알림

**목표:** 상담 가능 시간 설정부터 예약·상담 완료·기록 작성·후속 업무까지 **업무 흐름이 끊기지 않도록** 구현한다.

### 3.1 담당 기능

| 하위 영역 | 구체 작업 | 기능명세 연관 | 단계 |
|---|---|---|---|
| 가능 시간 | 담당자별 상담 가능한 요일·시간대, 휴가·부재, 불가 시간 | CAL-01~02 | 1 |
| 예약 | 상담 신청, 수락·거절, 변경 요청, 취소, 중복 일정 검증 | CAL-03~07 | 1 |
| 예약 결과 | 불참, 재예약, 상담 완료 및 완료 코멘트 | CAL-08~09 | 1 |
| 상담 연결 | 완료된 예약을 상담 기록과 연결, 예약 없는 방문·외부 전화 상담 기록 | CAL-10, REC-01 | 1 |
| 상담 기록 | 내용 직접 입력·목록·상세·수정, 수정자/수정 시각/변경 버전 | REC-01, 05~08 | 1 |
| 상담 인계 | 담당자 간 대상자·상담 기록 전달 요청·상태 관리 | REC-10 | 정책 결정 후 |
| 후속 확인 | 담당자 확인 항목 등록·조회·완료·취소, 상담과 연결 | UX-04 및 MVP 후속 원칙 | 1 |
| 기본 통계 | 대상자별 누적 상담 횟수, 최근 상담일, 일정 상태 | REC-08 | 1 |
| 알림 | 예약·변경·취소·임박·상담 결과·AI 완료 알림, 알림 목록/읽음/설정 | NTF-01~08 | 1 |
| 실시간 상담 | 상담 시작 10분 전 입장, 세션 상태, 통화 재연결, 상담 종료 | CNS-01~04, 06~08 | 2 |
| 채팅 | 메시지 전달·실패/재전송·상담 기록 연결 | CNS-05~06 | 도입 시점 미정 |

**소유 경계:** BE 2는 상담 **기록 자체와 예약 상태**를 소유한다. OCR/STT의 원본 파일·변환 작업·AI 결과는 BE 3이 소유하고 상담 기록 ID로 연결한다.

### 3.2 소유 데이터 예시

- `staff_availability` — 주간 가능 시간
- `availability_exceptions` — 휴가·부재·예외 시간
- `appointments` — 예약 참여자/시간/종류/상태
- `appointment_change_requests` — 일정 변경 제안과 응답
- `consultations` — 상담 기록 및 관련 예약
- `consultation_versions` — 상담 기록 수정 이력 및 버전
- `follow_up_tasks` — 후속 확인 업무/기한/상태
- `notifications` — 알림 종류·수신자·읽음/발송 상태
- `handover_requests` — 상담 인계 요청(정책 결정 후)
- 2단계 `call_sessions`, `chat_messages` — 실시간 상담 관리(실제 데이터 소유 범위 협의)

### 3.3 API 영역 예시

- `GET/PUT /api/availability` — 가능 시간 조회·등록
- `GET/POST /api/appointments` — 일정 조회·상담 신청
- `POST /api/appointments/{id}/accept` — 수락
- `POST /api/appointments/{id}/reject` — 거절
- `POST /api/appointments/{id}/reschedule` — 변경 제안
- `POST /api/appointments/{id}/cancel` — 취소
- `POST /api/appointments/{id}/complete` — 완료
- `GET/POST /api/consultations` — 상담 기록 조회·생성
- `GET/PATCH /api/consultations/{id}` — 상담 상세·수정
- `GET/POST/PATCH /api/follow-ups` — 후속 업무
- `GET/PATCH /api/notifications` — 알림 조회·읽음 처리
- 2단계 `/api/calls/*` — 통화 입장·세션 관리

> 경로와 HTTP 메서드는 **협업용 초안**이며 확정 API가 아니다. 개발 전 OpenAPI로 정리한다.

### 3.4 비즈니스 규칙 및 인수 테스트

- 요청자와 상대방의 배정/가족 연결 권한을 검증한다(BE 1의 공통 권한 사용).
- 담당자와 대상자의 예약 시간 충돌을 검사한다. 동시 수락 요청에도 **중복 확정 예약이 생기지 않아야 한다.**
- 예약 상태 전이는 허용된 요청자·상태에서만 실행한다.
- 변경 요청이 기존 확정 일정을 언제 변경하는지 정책을 명확히 한다. **기본 권고:** 상대방이 수락하기 전에는 기존 일정을 유지한다.
- 완료된 상담에는 담당자·완료 시각·코멘트가 남고, 추후 작성한 기록도 연결할 수 있다.
- 상담 기록 수정 시 기존 내용과 수정자/시각을 추적할 수 있다. AI 분석이 참조한 텍스트 버전은 BE 3과 합의한다.
- 후속 업무 완료는 **문제 해결** 또는 **복지 자격 확정**을 자동으로 의미하지 않는다.
- 푸시 발송 실패가 이미 확정된 예약을 취소하거나 유실시키지 않아야 한다.
- 2단계 통화 입장 제한은 화면뿐 아니라 서버에서도 검증한다.

### 3.5 BE 2의 독립 로컬 테스트 순서

1. **Phase 1:** 공통 형식의 로컬 프로젝트 생성, PostgreSQL 연결, 가상 계정/담당자 배정 fixture 생성, `/health` 테스트
2. **Phase 2:** 상담 가능 시간 조회·등록·예외 시간 API
3. **Phase 3:** 예약 신청 → 수락/거절 → 캘린더 조회 및 동시 예약 충돌 테스트
4. **Phase 4:** 상담 완료 코멘트·기록 직접 입력·목록·조회·수정 버전 테스트
5. **Phase 5:** 후속 업무 등록/완료와 예약·결과 알림 테스트
6. **Phase 6:** BE 1 인증 모듈·BE 3 분석 결과·프론트엔드 API 연동 테스트
7. **후속 단계:** 통화/영상·채팅(승인된 범위에서만)

팀 프레임워크가 아직 정해지지 않았다면 **ERD, 상태 전이표, OpenAPI, 테스트 시나리오**를 먼저 확정한다. 임시 Express 코드를 작성하더라도 팀에서 다른 프레임워크를 결정하면 재작성이 발생할 수 있다.

임시 `X-Test-Actor` 같은 가상 인증 헤더는 **로컬 테스트 환경에서만** 허용한다. 실제 배포 빌드에서는 사용하지 않는다.

## 4. BE 3 — AI·OCR·STT·복지 정보

**목표:** 상담에서 얻은 텍스트·상담지 사진·녹음 파일을 신뢰 가능한 분석 입력으로 정리하고, 근거를 검증한 AI 결과와 복지사업 확인 후보를 제공한다.

### 4.1 담당 기능

| 하위 영역 | 구체 작업 | 기능명세 연관 | 단계 |
|---|---|---|---|
| 사진 OCR | 상담 메모/상담지 사진 업로드, 문자 추출, 결과 확인·교정 | REC-02, REC-05, REC-09 | 1 |
| 음성 STT | 녹음 파일 업로드, 음성→텍스트, 전사 오류·재처리 | REC-03, REC-05, REC-09 | 1 |
| 화자 구분 | 가능한 경우 발언자 구분, 담당자 교정·확정 | REC-04 | 1 |
| 원본/교정본 | 업로드 원본·추출 원본·담당자 교정본, 버전 식별 | REC-06, AI-05 | 1 |
| 현재 상황 요약 | 건강·주거·소득·가족·정서 등 원문에 있는 사실 중심 요약 | AI-01 | 1 |
| 변화 분석 | 이전·현재 상담 비교, 악화·개선·변화 없음·정보 부족 구분 | AI-02 | 1 |
| 누적 분석 | 여러 상담의 반복 문제·변화 추이 | AI-03 | 1 |
| 다음 상담 질문 | 확인이 필요한 사실과 후속 질문 제안 | AI-04 | 1 |
| 근거 검증 | 원문 인용·기록/발언 ID·참조 버전·스키마 검증 | AI-05 | 1 |
| 담당자 검토 | 분석 초안·담당자 수정본·승인 결과 분리 | AI-06~08 | 1 |
| 복지사업 정보 | 후보/상세·공식 출처·확인일·자격 미확인 표시 | WEL-01~04 | 1 |
| 위기 신호 알림 | 정확도·대응 정책 검토 후 결정 | AI-09 | **미확정 후보** |
| 실시간 상담 연계 | 2단계 통화 음성·대화 기록을 상담 분석에 연결 | CNS-06~08 | 2 |

**범위 주의:** 현재 통합 명세서의 사진 기능은 **상담지·메모 사진에서 글자를 추출하는 OCR**이다. 사진 속 생활환경의 영상적 해석은 이 문서에서 확정된 기능이 아니다. 영상통화 **영상 자체의 AI 분석도 포함하지 않는다.**

### 4.2 소유 데이터 예시

- `media_assets` — 업로드 파일 및 처리 상태
- `ocr_results` — OCR 원문·수정본
- `transcripts`, `transcript_segments`, `transcript_versions` — STT 원문/발언자/교정 이력
- `ai_analysis_runs` — 분석 실행·상태·실패·멱등키
- `ai_analysis_results` — AI 초안·검토 결과
- `analysis_evidence` — 원문 인용·참조 버전
- `welfare_programs` — 복지사업 목록·출처·갱신 상태
- `welfare_recommendation_snapshots` — 분석 시점의 사업 후보 정보

### 4.3 API 영역 예시

- `/api/media/*` — 파일 업로드/처리 결과
- `/api/ocr/*` — OCR 요청·결과·교정
- `/api/transcripts/*` — STT 요청·결과·화자 교정
- `/api/analyses/*` — 분석 실행·상태·근거·결과
- `/api/analysis-reviews/*` — 담당자 검토·승인
- `/api/welfare-programs/*` — 복지사업 정보·후보

### 4.4 분석 안전 규칙 및 인수 테스트

- AI 결과는 입력 자료에 없는 사실·진단·복지 자격을 만들어 확정하지 않는다.
- **정보 부족(`unknown`)과 변화 없음(`unchanged`)을 반드시 구분**한다.
- 주요 분석 내용에 사용한 기록 ID·원문 또는 교정된 전사 구간·버전 식별자를 연결한다.
- 원문에 존재하지 않는 인용 또는 잘못된 스키마는 검증 실패로 처리한다.
- 분석 실패·시간 초과·검증 실패 시 결과를 성공으로 표시하지 않으며 상담 원문을 삭제하지 않는다.
- 동일 분석 요청의 네트워크 재시도로 중복 실행되지 않도록 멱등성을 고려한다.
- AI 초안, 담당자 검토·수정본, 대상자 공개 결과를 구분한다.
- 복지사업 후보는 자동 수급 판정이나 자동 신청이 아니다. `자격 미확인` 상태와 공식 출처를 제공한다.
- 합성 MVP의 4범주, 20초/45초 처리 시간, 분당 호출 제한, 2개 고정 사업 등은 **참고 규칙**이며 확장 앱 최종 운영값으로 확정하지 않는다.

### 4.5 타 담당자에게 제공할 계약

- BE 2에 `consultation_id`, `record_version_id` 기반 분석 시작/결과 조회 인터페이스
- BE 2에 분석 완료·실패 이벤트 및 공개 승인 상태
- BE 1의 권한 검사를 적용한 파일/AI 결과 열람 API
- 프론트엔드에 진행 중·성공·실패 상태와 검증 근거의 표준 응답

### 병렬 개발을 위해 반드시 먼저 합의할 계약

1. **식별자:** `user_id`, `person_id`, `staff_id`, `appointment_id`, `consultation_id`의 의미와 타입
2. **사용자 권한:** 승인/배정/가족 연결 여부를 확인하는 공통 함수 및 에러 형식

6. **API 계약:** OpenAPI, 날짜/시간대, pagination, 공통 오류 구조
7. **동의 및 공개:** 녹음/AI 사용 동의 확인 주체와 대상자·가족에 공개할 정보 범위

## 6. 개발 단계별 분담

| 단계 | BE 1 | BE 2 | BE 3 | 공동 완료 기준 |
|---|---|---|---|---|

| **1. 기본 흐름** | 가입·로그인·담당자 승인·가족 연결 | 가능 시간·예약 요청·수락·캘린더 | OCR·STT 업로드 및 교정 | 가상 대상자-담당자 주요 흐름 동작 |
| **2. 기록·AI** | 자료 접근 권한 강화 | 상담 완료·기록 수정·후속 업무 | 상담 요약·변화 비교·누적 분석·근거 검증 | 기록→AI→검토·후속 연결 |

| **4. 통합 검증** | 접근 차단·권한 회수 | 예약 충돌·상태 전이 | AI 출력/근거 검증 | 프론트엔드 E2E, 회귀 테스트 |

## 9. 팀 운영 제안

- **공통 프로젝트:** 초기에는 하나의 백엔드 저장소에서 도메인별 모듈을 나누는 방식(모듈형 모놀리스)을 권장한다. 마이크로서비스 분리는 운영 필요성이 검증된 이후 결정한다.
- **브랜치/PR:** `feature/auth-*`(BE 1), `feature/appointments-*`(BE 2), `feature/ai-*`(BE 3)처럼 모듈별 작업 브랜치를 사용한다.
- **API 우선:** 프론트엔드와의 연동을 위해 구현 전 또는 구현 초기부터 OpenAPI와 Mock 응답을 공유한다.
- **일일 공유:** 완료한 API, 변경된 DB, 실패 테스트, 다른 담당자에게 필요한 결정을 간단히 공유한다.
- **통합 순서:** 인증/관계 → 예약/상담 기록 → AI/파일 → 후속 업무/알림 → 관리자/실시간 상담.
- **품질 기준:** 동작하는 화면만으로 완료를 선언하지 않는다. 권한·경쟁 상태·오류·원문 근거·재시도를 테스트한다.

## 10. 한 줄 정리

- **BE 1:** **누가** 사용할 수 있고 **어떤 자료에** 접근할 수 있는지 책임진다.
- **BE 2:** 상담을 **어떻게 예약·진행·기록하고 후속 처리할지** 책임진다.
- **BE 3:** 상담 자료를 **어떻게 텍스트화·AI 분석·근거 검증하고 복지 정보로 연결할지** 책임진다.

세 영역은 독립적으로 개발하되, **권한·상담 기록 ID/버전·분석 완료 이벤트·API 계약**을 공통으로 관리해야 통합 시 재작업을 줄일 수 있다.
